# QQ 群聊增强

让群里的机器人结合上下文，判断一句话是不是在对自己说。

@、引用和关键词仍然可以直接叫醒机器人；像“那你更推荐哪个？”这样的自然追问，则交给 **Jev** 判断是否需要接话。Jev 只负责判断，回复仍由 AstrBot 中配置的聊天模型生成，人设、工具和会话历史继续沿用。

## 💬 怎么接话

| 群里发生了什么 | 插件如何处理 |
| --- | --- |
| @机器人、引用机器人，或说出配置的关键词 | 直接唤醒，跳过 Jev |
| 机器人处于清醒状态，有人继续发消息 | 聚合一小段时间后，结合上下文交给 Jev 判断 |
| 机器人已不清醒，但刚发言后的消息还不多 | 默认只检测它最近发言后的前 **5 条**消息 |
| 非清醒时，已超出条数范围或尚未观察到机器人发言 | 只记录历史，不请求 Jev |

默认用 **5 秒**窗口收集符合条件的消息，搭配最近 **30 条**历史逐条判断。同批只要有仍有效的消息达到 **0.75** 的阈值，就最多新增一次唤醒。

这些数字都能在配置页调整。清醒不代表每句话都会回复，是否接话仍由 Jev 判断。

## 🚀 快速上手

需要 **AstrBot `>=4.27.4,<5`**、Python 3.12+，以及 `aiocqhttp` / NapCat OneBot v11。语义唤醒使用 AstrBot **本地 Agent 执行器**。当前回归测试基于 AstrBot **4.27.4**，新版本的内部接口仍需验证。

1. 将插件目录放入 `data/plugins/astrbot_plugin_qq_group_enhance`，在 AstrBot 中加载插件。
2. 打开插件配置，在 **Jev 语义唤醒**中填写 API Key。默认请求官方接口；使用代理时，填写兼容 Jev 的完整接口地址。服务说明见 [TypeSafe AI 文档](https://docs.typesafe.ai/introduction/quickstart)。
3. 在 AstrBot 中开启 **群聊消息记录注入上下文**，不需要开启“持久化群聊消息记录”。
4. 群内共享对话时，建议关闭 **会话隔离**。默认 AI 聊天的 `provider_settings.wake_prefix` 留空；使用本插件的关键词时，从 AstrBot 自带唤醒前缀中移除同名词，避免正文提前被删改。
5. 保存配置并重载插件。先 @机器人聊一句，再发送不带 @ 的追问，观察它是否接话。

只使用关键词、@和引用唤醒时，可以关闭 Jev 开关，无需填写密钥，也无需开启群聊上下文注入。关键词默认留空，需要昵称唤醒时自行添加。

> 从旧版升级？请先保留原配置，并查看下方的「升级说明」，再加载新版插件。

## ⚙️ 按习惯调整

### 关键词唤醒

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 直接唤醒关键词 | 空列表 | 正文包含任意关键词就唤醒；留空关闭关键词匹配 |
| 关键词不区分大小写 | 开启 | 例如 `Airi` 可匹配 `airi`、`AIRI`；关闭后严格区分 |

这个分组不设单独的启用开关，关键词匹配保留消息原文。

### Jev 语义唤醒

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 启用 Jev 语义判断 | 开启 | 只控制语义判断，不影响关键词、@和引用唤醒 |
| Jev 请求地址 | `https://api.typesafe.ai/v1/systemone` | 完整 HTTP(S) 接口地址，不自动追加路径 |
| TypeSafe AI / Jev API Key | 空 | 留空时暂停语义判断，插件仍可加载 |
| Jev 固定模型版本 | `jev-1.13.0` | 使用固定版本，不接受 `latest` 或 `preview` 别名 |
| 群共享清醒时长 | 180 秒 | 本轮模型回复成功发送后刷新 |
| Jev 消息聚合窗口 | 5 秒 | 从首条待判消息开始计时，后续消息不延长窗口 |
| 非清醒时距机器人最近发言的最大消息条数 | 5 条 | 仅限制非清醒状态；清醒时不受此限制 |
| Jev 历史消息缓存条数 | 30 条 | 待判消息另外保存，不占历史额度 |
| 逐条语义判断通过阈值 | 0.75 | 大于 0 且不超过 1；越高越保守 |
| Jev 单次请求超时 | 10 秒 | 每次请求独立计时 |
| Jev 失败后的重试次数 | 1 次 | 设为 0 时不重试 |

觉得接话太频繁，可以提高阈值；经常漏掉追问，可以适当降低阈值。想缩短等待时间，可以缩短聚合窗口，但这也可能增加请求次数。实际回复还需要等待 Jev 判断和聊天模型生成，5 秒只是收集消息的时间。

关闭 Jev 开关后，相关参数会隐藏并保留原值。插件继续记录内存历史，但不建立待判窗口、不请求 Jev。配置修改需要保存并重载，重载会清空内存历史。

## 🧠 清醒、上下文与回复

**什么时候清醒？** 机器人在非清醒状态下被设置为唤醒，就进入清醒状态。不论这次唤醒来自核心、其他插件还是本插件，规则一致。清醒中再次唤醒不续期，只有本轮模型回复成功发送到群后，才刷新为发送完成时刻加配置的清醒时长（默认 180 秒），即使发送前已经过期也会重新清醒。流式、分段回复以整轮发送完成为准，部分发送失败、仅得到模型结果或工具内部发送都不刷新。

清醒状态按群共享。同一个群里的成员共用期限，不同平台实例和群之间独立；开启 AstrBot 会话隔离时，实际回复仍遵守成员各自的会话边界。

**“最近发言后的 5 条”怎么算？** 从机器人最近一次成功发出的群消息之后开始计数，包含当前消息，指令和图片等也算一条，重复上报不重复计数。清醒到期不会重新计数；机器人再次成功发言才重置，包括分段、工具输出和指令回复。这与“整轮模型回复成功后刷新清醒”是两件事。距离没有额外的时间限制。

**历史放在哪里？** 本插件维护纯内存缓存，保存群聊消息和机器人实际发言。历史、待判窗口、正在判断的批次分开存储，所以一批消息超过 30 条也不会只判断最后 30 条。重载、重启或会话重置后重新积累，不从 NapCat 补拉历史。

**会重复处理群消息吗？** Jev 判断通过后启动独立回复任务，原消息不会重新进入入站队列。已经实际送入聊天模型的消息会从待判范围中移除；仅仅收到消息或处于防抖等待中，不算已被模型处理。这个判断依赖输入内容仍能对应到原消息，被其他插件改写或摘要后的内容可能再次参与判断。

**能和 QQ 增强一起用吗？** 可以，也支持单独使用。@、引用和关键词等直接唤醒仍可走 QQ 增强的防抖流程；**Jev 触发的回复暂不参与 QQ 增强防抖**，不会再叠加一次防抖等待。两种回复目前不会统一合并，连续触发时可能分别回答。

**Jev 出错怎么办？** 按设置重试，耗尽后跳过该请求负责的判断并归档消息，不因失败新增唤醒。正常的否定结果不重试，也不会拦截消息或撤销其他来源的唤醒。超限拆分时，其他子批和下一窗口继续处理；一次失败不会清空整个群的待判消息。

## 🔎 没接话时看这里

先在 AstrBot 控制台开启 **INFO** 等级，并显示插件日志。

| 可以搜索的日志 | 能看到什么 |
| --- | --- |
| `Jev 判断完成` | 耗时、模型、Token 用量，以及逐条消息的概率、阈值和有效性 |
| `Jev 唤醒汇总` | 当前群的候选数、有效通过数、是否新增唤醒 |
| `Jev 请求回复` | 是否已提交独立回复任务 |
| `Jev request failed` | 请求失败类型、尝试次数和耗时 |
| `Jev 语义唤醒未运行` | 执行器或群聊上下文注入等前提条件未满足 |

**完全没有 Jev 日志？** 先检查 Jev 开关、API Key、本地 Agent 执行器和群聊上下文注入。确认消息没有超出非清醒时的检测范围，也没有被会话停用、白名单或其他插件阻止。直接 @、引用和关键词唤醒本来就会跳过 Jev，因此不会出现判断结果日志。

**概率达标却没回复？** 还要看消息是否仍有效。它可能已经被另一轮回复的输入覆盖，也可能在排队期间发生会话重置或停用。“请求回复”表示任务已提交，最终仍可能取消或发送失败。

**配置填错了？** 插件会保留加载状态和 WebUI 配置入口，在日志中给出原因；本插件功能暂停，修正配置并重载后恢复。单纯没有填写 API Key 或关闭 Jev 开关时，直接唤醒和历史记录仍正常工作。

## 🔐 群聊数据去向

语义判断会将群聊历史、待判消息和已有媒体描述发送到配置的 **Jev 请求地址**，默认使用 TypeSafe AI。自定义接口需要兼容 Jev 的 JSON 协议及 `Authorization: Bearer` 鉴权。

Jev 接收文本。插件会复用判断时已取得且能关联到原消息的图片描述、语音转写和引用信息；没有结果时只提供图片、语音等类型占位，不发送媒体二进制、不额外识图或转写，也不延长窗口等待。占位不代表模型理解了媒体内容，纯图片或语音不会仅因消息类型而默认唤醒。@、引用和关键词等直接唤醒仍正常生效。

本插件的 Jev 日志记录判断结果与用量，不输出密钥或整段群聊正文；AstrBot 自身的入站消息日志仍遵循核心设置。

## 📦 升级说明

**升级前先保留原配置。** AstrBot 4.27.4 会在插件初始化前按新配置结构删除旧字段、补入默认值，插件自身的校验无法阻止这一步。已保存且字段仍有效的配置值不会因默认值调整而被覆盖。

<details>
<summary>从早期版本升级时需要调整哪些配置？</summary>

| 旧配置 | 现在怎么设置 |
| --- | --- |
| 顶层 `keywords` | 移入 `keyword_wake.keywords`，默认空列表 |
| `keyword_case_sensitive` | 改为 `keyword_wake.keyword_ignore_case`，含义相反；要保持原行为，应取旧值的相反值。新项默认开启 |
| 平铺的 Jev 参数 | 放入 `semantic` 分组，结构见上方完整配置 |
| `asleep_observe_seconds` | 删除。非清醒状态已取消全量检测，改为消息距离限制，与清醒状态共用聚合窗口 |
| `traffic_window_minutes`、`low_max_messages`、`medium_max_messages`、`count_bot_messages` | 删除。流量分级已移除 |

旧字段没有自动映射或兼容别名。插件收到废弃字段时会明确报错并暂停功能，仍允许进入 WebUI 修改配置。

</details>

## 🛠️ 开发与实现

以下保留窗口、去重和接口的关键约定，排查并发问题或修改实现时可以按需展开。配置定义见 [_conf_schema.json](_conf_schema.json)。

<details>
<summary>消息窗口与缓存：什么时候判断，什么时候归档</summary>

**正常入站流程始终继续运行。** 窗口计时和 Jev 请求在独立任务中执行，不让消息等待判断完成，也不把 Jev 当作进入聊天模型或 QQ 防抖的准入条件。标准指令按 AstrBot 原有流程分发，不进入普通聊天待判窗口。

第一条符合条件的消息开启固定窗口。是否入窗在到达时决定：后续消息不会延长截止时间，清醒到期或收到更多消息也不会撤销已入窗的候选。只作历史的消息不会因为机器人稍后发言而补入待判。

窗口到期后，固定本批候选及历史快照，消息 ID、发送者和顺序保持独立。判断期间符合条件的新消息进入下一窗口。同群的 Jev 请求、重试和拆分子批串行执行，不同群互不等待；上一批结束后，已到期的下一窗口可立即处理，提交前再次排除已失效消息。

| 消息处于什么阶段 | 保存与处理方式 |
| --- | --- |
| 无需判断的消息、机器人实际发言 | 直接进入历史缓存 |
| 当前窗口内的候选 | 放入待判集合，不占历史条数额度 |
| 已开始 Jev 判断 | 放入判断中批次，请求快照不随后续消息改变 |
| 判断结束，或该请求重试耗尽 | 转入历史；失败与有效否定分别记录，不反复送判 |
| 已触发唤醒，回复尚在排队或执行 | 转入历史，同时独立保留消息 ID 和覆盖跟踪，不因历史滚动而提前丢失去重依据 |
| 观察到消息已送入聊天模型 | 按 ID 排除其待判资格；已归档的只更新状态 |

历史按原接收顺序保留最近的消息，按 ID 去重，不按异步任务完成顺序排序，也不额外按时间过期。机器人最近发言的位置单独保存，归档、输入覆盖和历史淘汰不改变消息距离。重载、会话重置或群状态淘汰会清除此位置，需要再次观察到机器人发言才能恢复非清醒时的距离检测。

本插件的历史缓存服务于 Jev；AstrBot 的群聊上下文注入服务于聊天模型。原生注入缓存会在准备回复时消费记录，并不等同于一份持续保留的结构化群聊历史，因此两者分别维护。

</details>

<details>
<summary>防重复回复：按实际模型输入清理，不按时间清空窗口</summary>

覆盖观察位于 AstrBot 本地 Agent 完成上下文裁剪后、调用提供商 `text_chat` / `text_chat_stream` 的边界。插件通过完整原生群聊记录文本或已关联的输入结构指纹，识别实际包含的消息 ID；上下文注入和防抖带入的内容也按同一规则处理。

例如 Jev 正在判断消息 1～3 时收到 4、5，后两条先进入下一窗口。如果后续聊天模型输入实际包含 1～5，就将这些 ID 排除出待判；新来的消息 6 没有被包含，便继续留在窗口。防抖期间收到的消息同样要等实际输入包含后才清理，不能因为它们“在防抖期间到达”就提前移除。只有窗口已经为空时才取消计时。

**输入覆盖与回复成功是两个时点。** 前者清理待判，后者刷新清醒。发给 Jev、进入防抖等待、组装中的请求都不算聊天模型覆盖；调用提供商表示本地已提交调用，不代表远端已成功受理。提交后即使生成失败、取消或发送失败，也不恢复待判，重试与续接由原回复流程负责。

Jev 每次重试前和最终结果处理时都会重新检查候选。若消息 1 已被覆盖，而 2、3 均未达阈值，即使消息 1 的返回概率很高也不会唤醒；部分失效只忽略对应结果，其余有效结果继续使用，不为此重发整批。每个原批次最多新增一次唤醒。

通过判断后，以同会话最近有效消息的已预处理结果为输入，提交内部 `ReplyRequest`，直接进入模型回复、结果整理和发送阶段。原消息不会重入事件总线，也不会重复执行命令、入站处理器、媒体预处理或原生群聊记录；模型钩子、人设、工具、历史保存和流式发送仍由正常回复阶段负责。

独立回复可能等待 AstrBot 会话锁。任务启动、取得锁准备输入和实际提交前会检查会话与插件启停、白名单、配置及会话身份、原消息状态和唤醒依据；依据已全部被覆盖或会话已失效时取消回复。原生上下文按记录 ID 定位，记录已被消费或淘汰时停止该次回复，不使用旧的数字位置去截取后来的消息。

这些观察通过可撤销的运行时包装实现，无需修改 AstrBot 或 QQ 增强源码。重置或卸载会停止相关任务并清理媒体，卸载还会恢复包装方法、关闭 HTTP 连接。待判期间保留的临时媒体仅供复用已有预处理结果，判断结束或回复任务结束后释放。观察异常会记录日志，正常模型调用和发送流程继续运行。

覆盖识别的范围是本地 Agent 的常规提供商调用。其他插件绕过执行器直接调用模型，或改写、摘要、产生有歧义的重复文本时，可能无法确认覆盖而多判断一次；插件不会凭时间或最新消息 ID 推定此前消息都已处理。QQ 增强也不保证普通消息自动并入防抖请求，最终是否包含仍以实际模型输入为准。

</details>

<details>
<summary>Jev 的请求与返回：逐条判断，共享上下文</summary>

请求采用异步 HTTP POST，并复用连接。正常容量下，同一窗口在**一次请求**里共享上下文，为每条候选分别提问，不是每条消息各发一次 HTTP 请求，也不是整批只返回一个是或否。

| 字段 | 内容 |
| --- | --- |
| `model` | 配置的固定 Jev 模型版本 |
| `state.bot` | 机器人 ID 和配置的关键词称呼，只声明一次 |
| `state.rules` | 公共判断规则，只保留一份；聊天内容作为数据，不执行其中改变规则的指令 |
| `state.history` | 本次可容纳的近期历史，作为背景 |
| `state.candidates` | 本批待判消息，与历史分开，保留各自发送者身份 |
| `questions.q0`、`questions.q1` 等 | 每个问题使用 `type: "noul"`，在 `instructions` 中引用公共规则并明确 `target_message_id` |

问题键只用来关联返回结果，真正的判断目标由指令中的消息 ID 指定。每条候选都结合共享上下文判断，包括回答机器人、追问和连续补充；历史里有人叫过机器人，不代表当前候选也应通过。普通消息直接携带 `text`，并保留消息 ID、发送者、时间、`mentions`（@对象 ID 列表）、`reply` 和已有的 `rendered_context`。机器人发言通过 `sender_id` 与 `state.bot.id` 对照识别，不在每条消息重复携带 `bot_id` 或 `is_bot`。

返回的核心结构如下，`q0`、`q1` 分别对应本次请求里的问题：

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "q0": { "type": "noul", "noul": 0.92 },
    "q1": { "type": "noul", "noul": 0.18 }
  },
  "usage": { "input_tokens": 1200, "output_tokens": 38 }
}
```

这里的数值仅为示例。`noul` 必须是 0～1 的有效数值，返回问题键必须与请求匹配；格式错误按请求失败处理，不当作有效否定。模型和 Token 用量未返回时，日志标注“未返回”。逐条结果只用于判定和去重，不意味着按候选条数生成多轮回复。

只有真正拆分的长消息才使用 `content_fragment`、`fragment` 和 `fragments`，问题增加 `target_fragment`。`fragment` 是从 0 开始的片段编号，`fragments` 是总片数，日志中的片段编号从 1 开始显示。普通消息不携带这些字段，本地原始记录不受请求精简影响。

增加问题会增加输入长度，实际延迟和费用需要结合日志中的耗时、`usage` 以及所用服务的计费规则评估。升级固定模型版本后，也应重新检查中文群聊样本中的误唤醒、漏唤醒和阈值。

参考：[Jev API](https://docs.typesafe.ai/api)、[Noul](https://docs.typesafe.ai/primitives/noul)、[多问题判断](https://docs.typesafe.ai/patterns/fan-out)、[模型说明](https://docs.typesafe.ai/models)。

</details>

<details>
<summary>超时、长消息和积压：失败影响到哪里</summary>

单次请求默认超时 10 秒、失败后重试 1 次，即最多两次尝试，各自计时。拆分后的每个子批分别使用这个限制，所以 20 秒不是整个大批次的总耗时上限。超时、HTTP 错误或无效返回都会进入失败处理；正常否定不重试。

重试耗尽后立即将该请求负责的剩余有效候选归档为失败，后续只作历史，不反复送判。其他子批和下一窗口不受影响；其他子批仍有有效通过结果时，原批次依然可以唤醒一次。重试前会排除已覆盖或失效消息，语义开关关闭后不继续发起重试或尚未提交的语义回复。

输入超限时优先保留候选，减少本次请求中的较旧历史；仍放不下时，按消息顺序拆成子批。历史裁减只影响 Jev 请求，不删除内存历史，也不裁剪聊天模型输入。子批顺序执行，汇总后按有效结果决定是否新增一次唤醒。

| 保护项 | 当前上限与处理 |
| --- | --- |
| Jev 输入预算 | 共享 `state` 加最长问题不超过 24,000 字节，完整请求不超过 48,000 字节；按 UTF-8 JSON 估算，不是 tokenizer 实测 Token 数 |
| 单条长内容 | 正文、已有描述与引用统一序列化，每片控制在 10,000 字节预算内；全部片段成功时取最高概率，任一片段失败则整条记失败 |
| 每群待判窗口 | 最多 2,000 条，或正文合计 8 MiB；超限时将最旧候选记为容量失败并归档，记录 ERROR |
| 群状态数量 | 最多 512 个；优先淘汰已非清醒且无任务的空闲群，全部活动时记录错误并跳过本次观察 |

这些是当前实现的保护常量，不是 WebUI 配置项，也不是 Python 进程的内存硬上限。减少历史、拆分和容量淘汰都会记录日志；历史不足 30 条或候选超过 30 条本身不会触发丢弃。分片可能影响跨片段理解，应结合实际消息评估。

</details>

修改实现时，重点检查以下行为：

- 关闭 Jev 或缺少密钥时只记录历史，关键词、@和引用仍直接唤醒；废弃或非法配置保留 WebUI 修正入口。

- 判断期间或防抖期间被实际输入覆盖的消息退出待判，迟到的 Jev 结果不再次唤醒，未覆盖的新消息不被整窗清空。

- 语义回复不重放入站、不重复预处理；排队期间重置、切换会话或卸载后，旧任务不继续消费新上下文，临时媒体正确释放。
- 只有整轮模型回复成功发送才续期，工具输出和部分发送失败不续期；已提交模型但生成失败的消息不恢复待判。
